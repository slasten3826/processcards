Этот документ идёт **назад по пайплайну**. Модуль был написан кодом, минуя слои. Здесь он описан как контракт — тем, чем должен был быть до кода. Таблица и хаос следуют за ним.

Всё, что ниже, — описание существующего манифеста. Ни одного нового решения здесь не принимается.

## 1. Что это

Одна функция наблюдения и четыре вокруг неё.

```text
M.observe(state, opts)              -> observation
M.resolve_handle(state, obs, h)     -> card_id | nil, err
M.build_action(state, obs, intent)  -> action | nil, err
M.evaluate(observation)             -> счёт по наблюдению
M.format(observation)               -> текст
M.contract_version = "view.honest.v0"
```

`observe` читает состояние и не меняет его. Остальные четыре читают только наблюдение и состояние.

## 2. Единственное правило

```text
личность карты раскрывается  <=>  state_lib.is_known(state, card_id)
```

То есть при `known` или `revealed`. Исключений по зонам нет ни одного.

Могила выпадает из этого правила сама: `GRAVE_LAW` делает карту `revealed` при входе, поэтому могила видна целиком без отдельной оговорки.

## 3. Почему идентификатор нельзя печатать

```text
cards.minor_pair_from_index выводит op_a и op_b из числа в "MINOR-<n>"
идентификаторы козырей так же индексируют constants.TRUMP_CANON
```

Значит печать идентификатора скрытой карты раскрывает её пару полностью, даже если `info_state` соблюдён. Это причина, по которой обычного «не показывать перевёрнутое» недостаточно и потребовались ручки.

## 4. Ручка

```text
формат      H<n>, n растёт с единицы
именует     позицию, а не карту
стабильна   внутри одного наблюдения
не стабильна между наблюдениями
```

Порядок выдачи фиксирован, иначе ручки прыгали бы между вызовами на одной позиции:

```text
1. manifest, latent, targets, trump, play, runtime   по слотам
2. grave, trump_flow                                 по порядку
3. deck                                              только верх
```

Ручка выдаётся только карте, не удовлетворяющей правилу §2.

`observation.handles[h]` хранит `{zone = ..., slot = ...}` для слотовых зон и `{zone = ..., index = ...}` для остальных. Идентификатора карты там нет.

## 5. Своя рука

```text
рука видна держателю целиком, независимо от info_state
```

Ручек картам руки не выдаётся, идентификаторы печатаются.

## 6. Дека

```text
высота  всегда публична
верх    показывается по правилу §2, иначе получает ручку
```

Остальная дека не наблюдается вообще.

## 7. Что публично всегда

```text
размеры зон и занятость слотов
board_closed
counts: deck, hand, grave, trump_flow
hidden_count -- сколько ручек выдано
committed_slot -- если слот зафиксирован
```

Занятость слота — это факт о столе, а не о карте, поэтому она публична и для скрытой карты.

## 8. Поля взаимодействия

Появляются только если передан `opts.interaction`.

```text
phase
prompt
legal_operators
legal_directions
legal_target_slots     номера слотов
legal_targets          ручки для скрытых, идентификаторы для известных
advance_enabled
advance_reason
```

`legal_targets` собирается из `ix.legal.targets.cards`. Для карты, удовлетворяющей §2, кладётся идентификатор; иначе — ручка её позиции. Если позиция не попала в обход §4, ручка выдаётся здесь же, а не теряется вместе с вариантом.

Открытое: эта ветка недостижима. Обход §4 покрывает все слотовые зоны, могилу, поток и верх деки, а таргетинг сейчас не предлагает ничего вне этого множества. Проверено на 1600 наблюдениях: расхождений нет ни одного. Ветка либо получит обоснование от будущего закона таргетинга, либо должна быть снята — но снятие это решение, а не уборка.

`legal_action_count` появляется отдельно, из `opts.legal_action_count`.

## 9. Индекс позиций

Соответствие «позиция → ручка» строится внутри `observe` и **остаётся локальным**.

```text
at[zone .. ":" .. slot] = handle
```

Обратный индекс `card_id -> handle` не строится и не может: он положил бы идентификатор скрытой карты в само наблюдение, то есть ровно то, против чего написан модуль.

## 10. Граница действия

```text
resolve_handle   ручка -> card_id
build_action     намерение с ручкой -> действие с card_id
```

Существуют затем, чтобы агент мог **действовать** на скрытую карту, ни разу не прочитав её личность. Для осмотра не предназначены.

`resolve_handle` отказывает тремя причинами:

```text
unknown_handle    ручки нет в наблюдении
unknown_zone      зона из ссылки не существует
empty_position    позиция опустела
```

`build_action` копирует намерение, выбрасывает ключ `handle` и кладёт разрешённый идентификатор в `action.target.card_id`, сохраняя остальные поля цели.

## 11. Счёт

`M.evaluate` повторяет веса `game.evaluate_state` **кроме** слагаемого `hidden_trumps`, и считает CONNECT в манифесте только по картам, доступным по §2.

```text
одна переменная отличается -> два счёта сравнимы
```

Открытое: веса продублированы в двух местах и разъедутся при первой правке одного из них.

## 12. Формат

Текст, одна зона на строку, слоты как `1:PAIR | 2:PAIR`, скрытая карта как `?H<n>`, отсутствующая как `-`. После доски — строки взаимодействия из §8, каждая только если непуста.

Формат — для машины. Читаемость нужна ровно настолько, чтобы аномалия была заметна глазом.

## 13. Проверки

```text
1. для каждой карты с info_state == "hidden" её идентификатор
   не встречается в наблюдении
2. то же для текста M.format
3. контроль: та же проверка над inspect.snapshot обязана ПРОВАЛИТЬСЯ
4. каждая ручка разрешается в карту, стоящую на этой позиции
5. число ручек равно hidden_count -- держится ровно пока
   недостижимая ветка §8 недостижима, поэтому проверка ещё
   и сторожит её
6. карта руки видна всегда, при любом info_state
7. legal_targets не содержит идентификатора карты, не удовлетворяющей §2
```

Пункт 3 — единственное, что отличает работающую проверку от проверки, которая всегда зелёная.

Пункты 1-5 живут в `src/sim/observation_audit.lua`, пункт 7 — в `src/sim/session_check.lua`.

## 14. Чего модуль не делает

```text
не решает, что легально        это машина
не хранит знание игрока        знание живёт в info_state
не кеширует наблюдение         каждый вызов строит заново
не стабилизирует ручки между вызовами
```
