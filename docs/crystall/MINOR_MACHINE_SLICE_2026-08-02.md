`MINOR_MACHINE_LAW §6` задаёт правило — «ожидание выбора объявляется данными, а не веткой» — и оставляет форму открытой (`§11.4`). Настоящий срез форму закрывает.

## 1. Почему это первое, что переписывается в машине

Замер 2026-08-01:

```text
десять полей pending_* в state.lua
восемнадцать функций arm_/confirm_ в turn.lua
```

`arm_encode_target` и `arm_hidden_target` совпадают построчно и отличаются четырьмя вещами: имя поля, строки ошибок, число взводимых позиций, имя события. Так восемь раз.

```text
восемь целевых фаз есть восемь копий ОДНОЙ машины
```

`TURN_STEP_LAW §13.4`. И `TRUMP_MACHINE_LAW §5`: козырная машина механизм **потребляет, не изобретает**, а ей понадобится около двадцати взаимодействий. Механизм, написанный дважды, будет написан по-разному — это уже случилось с декой.

## 2. Запись ожидания

Одно поле вместо десяти:

```lua
state.pending_choice = {
    kind     = "<строка>",   -- чьё это ожидание. Ключ в таблице §4
    source   = <card_id>,    -- карта, открывшая фазу. Лежит в play
    operator = "<OP>",       -- оператор, открывший фазу, или nil у козыря
    slots    = { <позиция>, ... },  -- УПОРЯДОЧЕННЫЙ список, §3
    picked   = { <ответ>, ... },    -- что уже выбрано, по индексу slots
}
```

```text
ожидание ОДНО. Двух одновременных не бывает
```

Козырь, открывший ожидание, занимает то же поле: механизм один на обе машины, `MINOR_MACHINE_LAW §6`.

## 3. Позиция

```lua
позиция = {
    kind     = "card" | "slot" | "direction",
    legal    = { <card_id | номер слота | "left"/"right"> },
    optional = <булево, по умолчанию false>,
}
```

Форма ответа выражается **числом позиций и их видом**, а не отдельной веткой на каждое взаимодействие:

```text
hidden      1 позиция  card
encode      2 позиции  card, card       обе из одного legal
manifest    1 позиция  slot
flow        2 позиции  card, direction  разные виды
public      1 позиция  card
unrevealed  1 позиция  card
hand        1 позиция  card
operator    1 позиция  card             выбор оператора, legal = операторы
```

Проверяемое следствие, ради которого форма именно такая:

```text
ORACLE ред. 2 — шесть позиций вида card, и ПОРЯДОК picked есть ответ
```

Перестановка выражается тем же списком, что и выбор одной карты. Если бы позиция была одна, а «сколько» отдельным числом, `ORACLE` потребовал бы второго механизма — то, что `§6` закона запрещает.

## 4. Где живёт поведение

```text
в записи лежат ДАННЫЕ. Поведение лежит в таблице по ключу kind
```

```lua
-- src/core/choice.lua
M.DECLARATIONS = {
    hidden = {
        slots  = function(state, ctx) ... end,  -- построить позиции
        apply  = function(state, pending) ... end,  -- что сделать при подтверждении
        events = {pending = "hidden_choice_pending", armed = "hidden_target_armed"},
    },
    ...
}
```

Причина, по которой имя, а не функция прямо в записи:

```text
таблица грепается одним запросом и перечисляет ВСЕ взаимодействия игры
```

Двадцать восемь строк в одном файле видно целиком; двадцать восемь замыканий, разбросанных по вызовам, — нет. `state` при этом остаётся простыми данными, хотя сериализация его и не требует: журнал пишет сид и тексты действий, а не состояние.

## 5. Диспетчер

Одна пара вместо восемнадцати функций:

```lua
-- src/core/choice.lua
M.open(state, kind, ctx)     -- построить позиции и объявить ожидание
M.arm(state, answer)         -- взвести очередную позицию
M.confirm(state)             -- подтвердить, когда все обязательные заполнены
M.clear(state)               -- снять ожидание
```

```text
arm  кладёт ответ в ПЕРВУЮ незаполненную позицию, чей legal его принимает
     повторный тот же ответ снимает взвод. Поведение сохраняется
confirm отказывает, пока есть незаполненная обязательная позиция
```

Отказы возвращаются переходом с полем ошибки, а не голой парой на границе действия: `TRANSITION_LAW §7`, и это же снимает `MINOR_MACHINE_LAW §10.2`.

## 6. Форма кода совпадает с формой закона

`MINOR_MACHINE_LAW §10.1` называет класс дефекта: закон записан исключающим списком, код — включающим, и они расходятся молча.

```text
законное правило   срабатывает ВЕЗДЕ, КРОМЕ targets
код прототипа      срабатывает ТОЛЬКО в latent
```

Поэтому `legal` строится **вычитанием из области**, а не перечислением зон:

```lua
legal = all_matching(state, predicate) minus excluded_zones
```

```text
исключение называется ЯВНО и по одному месту на правило
```

Проверяемое следствие: козырь на вершине деки после `OBSERVE` не остаётся `known` — `DECK_LAW §3`. Сегодня остаётся.

## 7. Чем машина владеет и чем нет

`MINOR_MACHINE_LAW §2` и `§7`, здесь в виде утверждений для структурных проверок:

```text
ВЛАДЕЕТ    цикл хода, манифестная колонка, механизм выбора, зона runtime
НЕ ВЛАДЕЕТ дека и латент, очередь козырей, поле исхода, слой транзакции,
           рука, целевая зона
```

```text
машина не пишет в outcome ни разу
машина не извлекает из деки напрямую ни разу
машина не разрешает козыря никогда
```

`MINOR_MACHINE_LAW §8`. Первое и третье проверяемы уже сегодня, второе — после перевода на модуль деки.

## 8. События

```text
choice_pending    kind, source, operator, slots
choice_armed      kind, index, answer
choice_confirmed  kind, picked
choice_cleared    kind, reason
```

Имена нынешних восьми пар (`hidden_choice_pending`, `encode_target_armed`, …) сохраняются через `DECLARATIONS[kind].events`: эталоны трасс стоят на них, и менять их одновременно с механизмом значит смешать две миграции.

```text
общие имена ДОБАВЛЯЮТСЯ, частные НЕ УДАЛЯЮТСЯ
```

## 9. Вырожденные случаи

```text
arm без ожидания              nil, "no_pending_choice"
arm ответом вне legal         nil, "illegal_choice"
arm при всех заполненных      nil, "choice_complete"
confirm с незаполненной       nil, "choice_incomplete"
повторный arm тем же ответом  снимает взвод, ошибкой не является
open поверх ожидания          nil, "choice_already_pending". Двух не бывает
позиция с пустым legal        ожидание НЕ открывается, apply не вызывается
```

Последняя строка несущая: оператор, которому некуда целиться, обязан разрешаться вхолостую, а не вешать ход.

## 10. Проверки среза

```text
1.  open заводит ожидание        state.pending_choice не nil, slots построены
2.  arm кладёт в первую пустую   picked[1] заполнен, picked[2] пуст
3.  arm вторым ответом           picked[2] заполнен
4.  повторный arm тем же         взвод снят, ошибки нет
5.  arm вне legal                nil, "illegal_choice"
6.  confirm с незаполненной      nil, "choice_incomplete"
7.  confirm при полном наборе    apply вызван, ожидание снято
8.  open поверх ожидания         nil, "choice_already_pending"
9.  позиция с пустым legal       ожидание не открылось
10. разные виды позиций          flow: card затем direction, оба приняты
11. ШЕСТЬ позиций                порядок picked сохранён — форма ORACLE
12. КОНТРОЛЬ: kind без строки
    в DECLARATIONS               nil, "unknown_choice_kind"
13. СТРУКТУРНАЯ: полей pending_* ровно одно
14. СТРУКТУРНАЯ: функций
    arm_*/confirm_* в turn.lua   ноль
15. СТРУКТУРНАЯ: outcome         turn.lua не пишет в outcome
16. СТРУКТУРНАЯ: дека            turn.lua не извлекает из деки напрямую
```

Что ловит каждая:

```text
2, 3, 10, 11  форма ответа выражена позициями. Одиннадцатая — та,
              из-за которой форма именно такая: без неё ORACLE
              получит второй механизм
4             сохранение поведения прототипа. Тихая потеря удобства
9             оператор без целей разрешается вхолостую, а не вешает ход
12            КОНТРОЛЬ: без него опечатка в kind открыла бы пустое
              ожидание и ход встал бы молча
13, 14        единственность механизма. Свойство набора файлов
15, 16        границы владения, MINOR_MACHINE_LAW §8. Шестнадцатая
              зеленеет только после перевода на модуль деки
```

Проверки 1-12 поведенческие, строятся расстановкой. 13-16 структурные.

## 11. Ожидаемое расхождение эталона

```text
ожидается частично
```

Частные имена событий сохраняются `§8`, поэтому существующие трассы не двигаются. Добавляются четыре общих имени — на них трассы разойдутся ровно в местах добавления.

```text
эталоны перезаписываются ПОСЛЕ приёмки, вместе с перезаписью
модуля деки. Все переписывания — одной операцией
```

`DECK_MODULE_SLICE §11` держит то же правило.
